*Seebot: checking the reliability of bioinformatics software*

Lee Katz, Andrew Page and Nabil-Fareed Alikhan discuss Seebot, Nabil-Fareed’s prototype for assessing bioinformatics software and its repositories. They explore basic command-line expectations, testing, maintenance and security, asking how developers can make tools less fragile without mistaking every warning or quiet repository for poor software.

## In this episode

### Fix fragile tools upstream

Nabil-Fareed Alikhan presents Seebot as a prototype for assessing bioinformatics tools and their repositories. It is named after Torsten and inspired by his habit of opening issues about usability and code improvements, particularly requests to package tools in Bioconda. The show notes link the related paper, *Ten recommendations for creating usable bioinformatics command line software*.

The immediate motivation was a phage working-group discussion about building pipelines around fragile software. Nabil-Fareed questions why pipeline authors should keep compensating for problems in publicly available, open-source code rather than fixing them upstream. Seebot uses Conda and Bioconda to help obtain software, then examines its behaviour, source code, repository information, dependencies and security issues.

### Basic expectations for command-line software

The intended audience is developers and aspiring developers. Rather than criticising individual authors, Nabil-Fareed wants to identify common gaps and turn the results into practical guidance. Users might also use those expectations when asking developers for improvements.

The initial checks are deliberately basic: a README, working **--help**, an accessible version number, a licence and citation information. Reliable version reporting matters for recording what ran in a pipeline. Testing adds another layer: a Bash script running a toy dataset is better than nothing, but Nabil-Fareed argues for standard automated test frameworks, such as pytest for Python, with checks of lower-level functions. He also sees a need to bring security checks, already familiar to software engineers, into routine bioinformatics development.

### Maintenance needs context

Lee introduces *Ten quick tips to SNIFF out sustainable and secure scientific software*, which he encountered through Stephen Turner on Bluesky. He explicitly says he has not yet read the paper in full. Its SNIFF framework covers Source, Network, Interaction, Fit and Fragility: questions about origins, ecosystems, maintainer communication, suitability and dependencies.

Nabil-Fareed questions how activity-based expectations should apply to bioinformatics. Seebot collects days since the last release and non-bot commit, commits in the previous 12 months, files over 500 lines, and linting errors per thousand lines. His early observations include tools with up to a year since their last commit, and popular tools with around 1,000 days since their last commit that still work. He has not processed all of Bioconda.

The diagnostic-testing discussion adds a regulatory concern: academic software can be software of unknown provenance. Citation counts offer an indirect proxy for quality, but even 10,000 citations cannot establish exactly how a tool was developed or checked.

### What uv, the Makefile and Ruff do

Lee asks whether Seebot’s Makefile drives the assessment. Nabil-Fareed explains that it mainly provides convenient shortcuts for commands run through uv, which handles Python dependencies and the virtual environment. A test shortcut runs **uv run pytest**; the Makefile itself is not the assessment engine.

Ruff checks Python code. Nabil-Fareed contrasts it with Black, which he finds more opinionated, and describes common findings: unsorted imports, older string-formatting styles rather than f-strings, long lines, unused imports and unused variables. These are distinct from findings that may affect execution or security.

### Silent failures and security warnings

More concerning findings include subprocess calls that open shells and **try/except/pass** patterns that suppress exceptions. Nabil-Fareed describes how ignoring an upstream failure can let a tool continue until it produces garbled output much later, obscuring the original problem.

Bandit provides security checks, including warnings about apparent hard-coded passwords. A frequent warning concerns MD5. Nabil-Fareed explains that the concern is using MD5 to hash passwords, while bioinformatics tools may instead be hashing allele sequences or k-mers. The warning therefore needs interpretation in the context of what the code actually does. He describes Bandit as conventional software performing checks, not an AI system.

### Could AI help apply the guidance?

The hosts discuss packaging agreed bioinformatics conventions as skills for Claude or ChatGPT, so an assistant could inspect a repository and potentially fix routine issues. Nabil-Fareed supports the idea once the metrics and best-practice guidance have been settled and written up; it is a proposed extension, not a demonstrated Seebot capability.

Language choices also get a lighter discussion. Nabil-Fareed reports seeing more Rust alongside plenty of C and C++, while the hosts joke about using AI to rewrite popular tools as Perl one-liners.
